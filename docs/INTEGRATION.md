# Shazam連携の内部構成

この文書は収録ソースの実装を説明するものです。
Shazamの公開サイトをWebView2で操作する構成であり、
サイトの将来の動作や公式スマートフォンアプリと同等の精度を保証するものではありません。

## 認識の流れ

```text
選択したマイク
  → sounddevice / PortAudioでmono/int16を常時取得
  → 3秒以上の間隔で認識スロット到来
  → 4本のWebView2レーンから空きworkerを選択
      ├─ 空きあり: そのレーンをライブPCM配信対象にして認識開始
      └─ 全busy: スロットを保持し、最初に空いたworkerでライブ認識開始
  → Python側のlane専用キューでPCMを約80〜200ms単位にまとめる
  → stdin JSONでヘルパーへ送り、WebView2 WebMessageでページへ転送
  → Web AudioのMediaStreamとしてShazamページへ継続供給
  → Shazamページで認識
  → 原則は要求連番seq順に認識結果を整列
      └─ 古いheadが未応答でも、後続の連続2 seqが同一曲なら安全にheadを追い越す
  → 1回目はCandidate pending
  → 次の有効認識でも同一曲ならTemporal confirmation
  → 必要な場合だけ確定候補をApple/日本語メタデータで補完
  → 履歴・Qt通知
  → 既存のYouTube検索と再生
```

認識秒数設定と固定長リングバッファは廃止済みです。Shazamへは認識開始後のライブPCMを継続供給します。workerの準備状態と認識スロットは100ms間隔で確認します。
各レーンは独立したヘルパーとブラウザープロファイルを持ち、1つのヘルパー内では同時に複数の認識を行いません。WebView2の結果待ち期限はソース上で15秒です。

### 4レーン共有ワーカープール

4レーンは固定の時刻スロットを所有しません。次の認識時刻になると、前回使用レーンの次からround-robinで探索し、利用可能なレーンを1本選びます。

旧方式では各レーンが12秒周期で固定されていたため、認識が13～15秒かかると次の自分のスロットを丸ごとskipし、実質的な認識間隔が大きく伸びることがありました。現在は別レーンが空いていれば借用し、全4レーンがbusyでもスロット自体は捨てません。

全busy時は過去時点のWAVやPCMをqueueに積みません。レーンが空いた時点から**未来へ流れるライブPCM**を受け取り始めるため、待機時間中に古くなった音声を後から認識することを避けています。

また、busy解消後に遅れたスロットを連続実行するcatch-upは行いません。実際に1本投入した時刻を基準に、次回は3秒後以降とします。これにより2回連続確認に使う音声の時間差も維持します。

4レーン・3秒間隔の理論上の処理能力は平均認識時間12秒です。認識が恒常的に12秒を超える場合は完全な3秒周期にはできませんが、固定12秒スロットを捨てる旧方式より、空き次第再開することで待ち時間を最小化します。

### 時系列2回確認

誤検出対策では同じWAVを2本へ複製しません。3秒以上ずれて開始した独立したライブ認識結果を、原則として要求連番`seq`順に比較します。

- 最初の有効結果は`Candidate pending`として内部保持します。
- 次の有効結果が`is_same_track()`で同一曲なら`Temporal confirmation`として確定します。
- 異なる曲ならその単発候補は確定しません。
- `no-match`が通常の時系列処理に入った場合は連続確認を切ります。
- workerの応答順が逆転しても、通常は`seq`順に並べてから判定します。
- 例外として、現在待っているhead `seq`が未応答でも、後続の**連続した2つのseq**が両方完了し、`is_same_track()`で同一曲なら、その2件を十分な独立証拠としてheadを追い越します。
- 後続が1件だけ、または連続2件が不一致なら追い越しません。したがって単発の誤認識だけで新曲確定することはありません。
- headを追い越した後に古い結果が遅れて返っても、その`seq`はstaleとして無視します。

例: `seq100`が15秒以上遅延し、`seq101=A`、`seq102=A`が先に揃った場合、`101/102`でAを確定できます。`seq101=A`だけでは`seq100`を待ち続けます。

同曲判定は既存仕様を変更せず、曲名先頭4文字一致を最優先とします。Shazamのoffsetは確定判定には使用しません。

## メタデータ

既存の`itunes_metadata.py`を維持しています。
速度低下を避けるため、メタデータ補完は各レーンのShazam認識中には実行しません。
まず時間差のある2回の生Shazam結果で確認します。`jsonld`や`recognition-response`など信頼できるrequest-scopedな結果に曲名とアーティストが両方そろっている場合は、そのWebView表示をそのまま採用してApple通信を省略します。
route-onlyや情報不足の場合だけ、採用された1曲について別スレッドで1回補完します。
そのためApple通信中も4本のShazamレーン自体は次の認識へ進めます。

実AppleリンクのID、認識ルート、曲名とアーティストの一致など、
既存の根拠に応じてLookup/Searchと日本語メタデータの補完を行います。

収録版のPython実装は`/song/<id>`と`/track/<id>`を区別しています。
`/song/`のIDについては既存実装の完全一致Lookup経路を使い、
`/track/`ではルート名等による追加の照合を維持しています。
今回の4文字一致は**アプリ内の連続検出のまとめ方**だけに用い、
Apple候補の選別やYouTube検索クエリーの照合条件には流用していません。

## 同曲判定と通知

`track_matching.py`の`is_same_track()`に判定を集約しています。
曲名先頭4文字の一致を先に判定し、不成立なら従来の判定へ進みます。
比較用の空白除去・大小文字の正規化もこのモジュールで行います。

同曲だった場合も直前の確定結果と要求連番は更新し、
履歴追加、JSON保存、`history_updated`、`new_track_detected`だけを抑止します。
ステータス通知と認識の継続は止めません。
アーティスト未取得の履歴も、読み込み時に捨てずに保持します。

`deduplicate_history()`は新しい順の履歴を並べ替えず、
元の隣接行を比較して各まとまりの先頭を残します。
離れた同曲を一括削除する処理ではありません。

## 公開インターフェース

UIが使うメソッドとシグナルは維持しています。

```text
start(), stop(), reload_settings(), shutdown(), is_active()
list_input_devices(), get_history()
history_updated(list)
new_track_detected((timestamp, title, artist))
status_changed(str)
error_occurred(str)
```

履歴のJSON項目は`timestamp`、`title`、`artist`のままです。
Shazamの認識秒数設定は廃止しました。音声は固定長WAVへ切り出さず、認識開始後のライブPCMを継続配信します。旧`shazam_recording_seconds`キーは既存設定の読み込み時に削除されます。

## ビルドと配布

実行手順は[README](../README.md)にまとめています。
ヘルパーのソース、埋め込みJavaScript、プロジェクトファイル、
マニフェストはすべて残しています。`bin/obj/publish`は再生成します。
`tools/finalize_build.py`はネイティブ依存関係を確認してから配布先へコピーし、
既存の設定・履歴を残します。

画面、動画ループ、検索順、MIDI・ホットキーは今回の変更対象外です。
検証済みと未検証の区別は[テスト手順](TESTING.md)を参照してください。
