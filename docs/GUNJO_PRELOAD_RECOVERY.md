# 「群青」が仮検索されるのに再生されない問題への対策（2026-10-13）

## 実機ログの解析

対象：`vj_yattaro(20261013-130213).log`、Shazam 曲ID `1618070130`、曲名「群青」、アーティスト「神山羊」。

| 時刻 | ログで確認した事実 |
| --- | --- |
| 22:01:06.618 | seq133で曲IDを1回認識（曲名は未取得） |
| 22:01:07.688 | 曲名「群青」取得、仮登録しYouTube先行検索開始 |
| 22:01:09.664 | 動画 `PEnzc0XE-OA` を最初の仮候補としてPRELOAD |
| 22:01:12.430 | 遅れて届いたseq135/136が同じ曲IDで一致（seq134は未完了） |
| 22:01:12.431 | 元の仮候補seq133を `older-observation-bypassed` として誤って破棄 |
| 22:01:12.449 | 同じ曲をseq135で改めて仮登録→確定。YouTube検索とPRELOADが重複 |
| 22:01:15.820 | 最初のPRELOADの`ready`応答が、異なるrequest IDとして無視された |
| 22:01:30.735 | 新しいPRELOADが15秒待ってもreadyにならず強制再送 |
| 22:01:30.931 | ようやくPLAYコマンドが送信されるが、次曲確定前にPLAYINGの記録なし |
| 22:01:35.133 | 次曲の検索で「群青」の未完了再生を取り消し |

ログ上は**曲IDの照合が誤ったのではなく、時系列追い越し処理で先行PRELOADの所有権が消えた**ことが一次原因です。さらにブラウザの再PRELOADに時間がかかり、次の曲までに再生が開始できませんでした。ブラウザが実際になぜ2回目のPRELOADで停滞したかは、このデスクトップログだけでは断定できません。

**実行EXEの版について:** 今回の実機ログにある `Tentative confirmed firstSeq=... secondSeq=...` は、直近のソースで採用した `temporalSeq=...` 付きのログ形式より古いものです。また、最新版にあった `Retaining tentative firstSeq=...` も実行されていません。このため、実行されたEXEが前回の最新ソースからビルドされていない可能性が高いです。

## 今回のコード対策

`app/services/shazam_service.py`:

- 追い越しに使う新しい**独立した2認識**が、表示中の仮候補と同一曲であることを検証します。
- 曲IDが一致し、元の仮候補が30秒以内のときは、**先行候補ID・YouTube検索・PRELOAD要求IDを維持**します。
- 時系列処理のQtイベントが遅れ、最後の認識の受領時刻から15秒以上経過しても、妥当な2認識ペアであれば先行候補を不要に取り消しません。
- 維持した最初の認識を追加の確認票として数えません。再生許可には、従来どおり有効な2認識の一致を必要とします。
- 30秒超の古い仮候補、曲IDの異なる候補、認識ペアが不一致の候補は引き継ぎません。
- ログに `Retaining tentative ... keep existing YouTube PRELOAD/request ID` と、維持しなかった場合の理由を出力します。

`main.py`, `app/version.py`:

- 起動ログへ `UI: Source build: 2026-10-13-gunjo-preload-v1` を記録します。古いEXEを起動していないかすぐ確認できます。
- 自動再生速度を下げるための遅延、仮表示の強制維持、Shazam 2回一致条件の緩和は実施しません。

## オフライン回帰テスト

`tests/test_gunjo_preload_regression.py` に以下7件を追加しました。

1. seq133→seq135/136（134未完了）の同曲追い越し時に仮候補とPRELOADを維持
2. PRELOADのREADYが2回目の認識より先に届いても早期再生しない
3. イベントループの遅延で通知処理が21秒遅れた場合も、30秒以内で同曲の先行PRELOADを維持
4. **実際の要求ID付き**PRELOAD/READY/PLAY/PLAYINGで、同一要求だけを受理
5. 30秒を超えた古い仮候補は再利用しない
6. 異なる曲の一致ペアなら元の仮候補を破棄
7. ソース版識別子の存在

旧版では項目3が失敗し、修正後は成功することを確認しました。検証はネットワーク・ブラウザなしのオフラインテストです。

## Windows実機確認手順

1. ZIPを**空のフォルダーへ展開**し、PowerShellで `./build.cmd` を実行します。
2. ビルドが完了したら、そのフォルダー内の `./dist/VJ_yattaro/VJ_yattaro.exe` を起動します。旧配布フォルダーに残ったEXEは使用しないでください。
3. 新しいログ冒頭に `UI: Source build: 2026-10-13-gunjo-preload-v1` が出ることを確認します。
4. 「群青」で1回目の仮登録→検索→PRELOADが始まったあと、別レーンの認識結果が先に届く状況を確認します。
5. 同曲なら `Retaining tentative firstSeq=...` が出て、再検索や2回目のPRELOAD送信を行わずに確定→PLAYになることを確認します。
6. 誤認識で別曲が2回一致したときは、旧候補が取り消されることを確認します。
